## Обычные тестировщики
- Участник создаёт обычный аккаунт через общую форму Supabase Auth.
- После подтверждения email и первого входа создаётся профиль с типом `tester`.
- Тестировщик не может изменить свой тип аккаунта, назначить себе школу или административную роль.
- Регистрация сама по себе не включает облачные разделы. До открытия отдельного staging все cloud feature flags остаются выключенными.

## Нестеров и другие администраторы
Администраторов назначает только взрослый владелец проекта в Supabase Dashboard → SQL Editor, отдельно от публичной регистрации и профиля.

Актуальная процедура и шаблон:
- `supabase/admin/README.md`
- `supabase/admin/assign_privileged_accounts.sql.template`

Для каждого человека:
1. Человек сам создаёт аккаунт и подтверждает email.
2. Он входит хотя бы один раз, чтобы создать профиль.
3. Владелец сверяет подтверждённый email с человеком и берёт UUID аккаунта в Authentication → Users.
4. В локальной копии SQL-шаблона владелец подставляет UUID взрослого оператора и UUID конкретных назначаемых аккаунтов.
5. Владелец запускает шаблон в SQL Editor и сверяет результат. Для отзыва доступа использует отдельный UPDATE из шаблона.

Не используй display name «Нестеров» как идентификатор — только сверенный UUID аккаунта. Не добавляй реальные UUID, email, пароли и ключи в GitHub или чат. Не назначай себе роль администратора через форму.

Текущая привилегированная роль — `verification_representative` в `role_assignments`; её проверяет серверная функция `is_verification_representative()`. Не применяй старую таблицу `platform_admins`.
