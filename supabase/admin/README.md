# Доступ тестировщиков и отдельное назначение администраторов

## Обычные тестировщики

Регистрация на сайте создаёт только обычный аккаунт тестировщика. Пользователь не выбирает себе должность, районное полномочие или административную роль. Поле `profiles.account_type` заполняется базовым значением `tester` на стороне PostgreSQL; клиент не может его изменить.

Для тестирования есть два режима.

### Режим A — закрытый пилот по приглашениям (рекомендуемый первый этап)

1. Взрослый владелец открывает Supabase Dashboard → **Authentication → Users**.
2. Нажимает **Add user → Send invitation** и вводит адрес конкретного участника тестирования.
3. Участник получает письмо, подтверждает адрес и завершает вход.
4. При первом успешном входе сайт создаёт облачный профиль; после применения миграции его серверный тип будет `tester`.
5. Администраторы назначаются отдельно по UUID через шаблон ниже.

Этот режим не включает самостоятельную регистрацию для всех посетителей сайта. Для внешних адресов всё равно понадобится настроенная доставка писем через собственный SMTP.

### Режим B — самостоятельная регистрация тестировщиков

Если нужен общий доступ по ссылке, взрослый владелец проверяет Supabase Dashboard:
1. **Authentication → General configuration** → включить **Allow new users to sign up**.
2. Оставить **Confirm Email** включённым. Не отключать подтверждение почты ради обхода ограничений.
3. Отключить **Allow anonymous sign-ins**.
4. В **URL Configuration** задать точный Site URL и разрешённые Redirect URLs для тестового сайта.
5. Настроить собственный SMTP для писем регистрации, подтверждения и восстановления пароля.
6. До широкого публичного открытия добавить CAPTCHA-защиту формы регистрации. В Supabase Auth поддерживаются hCaptcha и Cloudflare Turnstile; текущая форма Ынтымак ещё не передаёт `captchaToken`, поэтому нельзя включать обязательную CAPTCHA в Dashboard до отдельной интеграции этого компонента в интерфейс.

**Ограничение встроенной почты:** hosted Supabase по умолчанию отправляет письма только адресам участников организации; сейчас лимит — 2 письма в час на весь проект, пока используется встроенная почта. Внешние адреса получают отказ. Для тестировщиков из школ подключи custom SMTP и проверь доставку до приглашения группы. См. [общие настройки Auth](https://supabase.com/docs/guides/auth/general-configuration), [проверку Auth-потоков](https://supabase.com/docs/guides/auth/testing-auth-flows), [настройку SMTP](https://supabase.com/docs/guides/auth/auth-smtp) и [CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha).


В коде уже используется `supabase.auth.signUp()`. После подтверждения адреса человек входит с тем же email и паролем; при первом входе создаётся облачный профиль. До подтверждения адреса сессии может не быть — это нормальное поведение Supabase при включённом Confirm Email.

**Почтовое ограничение:** на hosted Supabase встроенная отправка Auth-писем (пока не настроен custom SMTP) отправляет письма только адресам участников организации и сейчас ограничена двумя письмами в час на весь проект; лимиты могут меняться. Для внешних школьников взрослому владельцу нужно заранее подключить собственный SMTP-провайдер и проверить доставку писем. Не отключай подтверждение email как обход этого ограничения. См. [настройки Auth](https://supabase.com/docs/guides/auth/general-configuration) и [тестирование Auth-потоков](https://supabase.com/docs/guides/auth/testing-auth-flows).

## Нестеров и другие администраторы

Административные полномочия **не назначаются в форме регистрации, профиле, публичном интерфейсе или через пользовательские метаданные**. Их выдаёт только взрослый владелец проекта отдельно в Supabase Dashboard → SQL Editor.

Файл `assign_privileged_accounts.sql.template` — шаблон этой закрытой процедуры. Он:
- принимает UUID существующих аккаунтов, а не display name;
- требует, чтобы адрес цели был подтверждён и профиль уже создан первым входом;
- отдельно указывает UUID взрослого оператора в `verified_by`;
- добавляет внутреннюю роль `verification_representative` сроком на 180 дней;
- не создаёт аккаунты и не задаёт пароли;
- не выдаёт доступ до подтверждения email;
- содержит секцию отзыва полномочий.

Для Нестерова и каждого администратора нужно сначала получить UUID существующего аккаунта в Authentication → Users. Сверь email с человеком вне чата, затем скопируй UUID. Вставь UUID в локальную копию шаблона в SQL Editor; **не добавляй реальные UUID, email или другие личные данные в Git и не присылай их в чат**. Само имя «Нестеров» не считается надёжным идентификатором: аккаунт определяется UUID.

### Разграничение полномочий

- **Тестировщик:** обычный пользователь; может входить, работать со своим профилем и использовать только те облачные модули, которые будут безопасно включены после тестирования.
- **Проверенный представитель / администратор платформы:** отдельная временная запись в `role_assignments`; доступ к управлению проверяется на сервере.
- **Президент школы, районный председатель и другие роли:** назначаются отдельной процедурой подтверждения; это не равно роли администратора платформы.

Обычный тестировщик не может самостоятельно вставлять, обновлять или удалять строки `role_assignments`. Текущий live ACL-аудит подтвердил отсутствие таких прав у роли `authenticated`.

## Порядок открытия внешнего тестирования

1. Взрослый владелец подтверждает настройки Supabase Auth и почтовую доставку.
2. Применяется миграция `20261115_tester_onboarding.sql` только после проверки полного набора патчей на staging.
3. Несколько добровольных тестировщиков регистрируются собственными email, подтверждают адрес и входят.
4. Проверяется, что у каждого появился тип аккаунта `tester`, а попытка изменить его или назначить себе роль не проходит.
5. Нестеров и администраторы получают полномочия отдельной закрытой процедурой из SQL Editor.
6. Только после проверки RLS и сценариев доступа взрослый владелец решает, какие конкретные модули разрешить тестировщикам.

До завершения этой последовательности облачные feature flags остаются выключенными. Регистрация аккаунтов сама по себе не означает, что публичный запуск всей платформы уже разрешён.
