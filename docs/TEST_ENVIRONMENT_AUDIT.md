## Найденные риски

### 1. Устаревшая функция списка участников

В базе существует `public.get_event_roster(text)`. Она получает мероприятие по event_key, а не по уникальному UUID. Её текущая логика допускает выдачу имени участника при public_name_consent, а организатору — дополнительных данных. Она не проверяет отдельное согласие на доступ организатора.

В репозитории есть новая версия `get_event_roster(uuid)`, которая ограничивает доступ конкретным мероприятием и возвращает только регистрации с organizer_access_consent=true. Но миграция этой версии не применена к рабочей базе.

**Решение:** не включать облачные списки участников до согласованного применения и тестирования новой модели на отдельной базе.

### 2. SECURITY DEFINER RPC

Supabase Advisor сообщает о пяти SECURITY DEFINER функциях, исполняемых ролью authenticated:
- can_manage_events()
- create_my_profile(...)
- get_event_roster(text)
- is_verification_representative()
- review_role_request(...)

Само наличие такого разрешения не доказывает уязвимость: часть функций предназначена для безопасного обхода ограничений таблиц. Однако каждую функцию нужно проверить на проверки auth.uid(), область данных, grants, search_path и сценарии отказа. Для устаревшей функции списка участников риск описан выше.

### 3. Дополнительное предупреждение Auth

В проекте отключена проверка паролей на утечки. Владелец проекта должен рассмотреть включение защиты в настройках Auth после проверки доступности этой функции для используемого плана.

### 4. Отсутствует история миграций

Существующие таблицы при пустой истории миграций указывают на возможный schema drift или создание схемы вне штатного migration workflow. Нельзя запускать весь каталог SQL-патчей вслепую или считать их применёнными.

## План тестирования

1. Сопоставить каждую миграцию из README с фактическими таблицами, колонками, ограничениями, индексами, политиками и функциями.
2. Построить таблицу зависимостей и определить безопасную точку старта тестовой схемы.
3. Подготовить чистую тестовую Supabase-среду. Создание Supabase development branch может тарифицироваться отдельно; до согласия на стоимость ветка базы не создаётся.
4. В тестовой среде применить миграции строго по порядку, затем выполнить проверки схемы и Supabase Security/Performance Advisors.
5. Создать только синтетические тестовые аккаунты и вымышленные записи.
6. Проверить отрицательные сценарии: чужой профиль, неподтверждённая роль, чужое мероприятие, отсутствие согласия на доступ организатора, повторная регистрация, прямой вызов RPC без входа.
7. Проверить интерфейс в Safari с тестовыми аккаунтами и подтвердить, что UI не показывает списки неавторизованным пользователям.
8. Зафиксировать результаты и только затем предложить владельцу отдельное решение о дальнейшем пилоте.
