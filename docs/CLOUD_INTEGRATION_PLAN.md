# План облачного подключения Ынтымак — 15 ноября 2026

## Что подтвердил аудит
Текущая база Supabase имеет 7 таблиц: `schools`, `profiles`, `role_catalog`, `role_requests`, `role_assignments`, `events`, `event_registrations`.

Фактическая модель событий отличается от локального демо:
- `events`: только `id`, `event_key`, `title`, `is_open`, `created_at`; допустимые ключи: `forum`, `media`, `debate`, `eco`.
- `event_registrations`: `event_id`, `user_id`, `participant_name`, `school_label`, `grade_label`, `participation_format`, `team_name`, `public_name_consent`, `status`, `created_at`. Уникальность — одна регистрация на пользователя и событие.
- `profiles.school_id` допускает NULL; каталог школ сейчас пуст.
- RLS включён на всех исходных таблицах.

## Изменения кода в этой ветке
- `cloud.js`: добавлены `listInitiatives()` и `createInitiative()`. Запросы используют текущую Auth-сессию, проверяют длину и контактные данные, а доступ к строкам оставляют RLS.
- `app.js`: отправка формы предложений может использовать облачный API при включённом флаге и активной Auth-сессии. При выключенном флаге поведение остаётся локальным демо.
- `supabase-config.js`: `enableCloudInitiatives: false`. Флаг намеренно выключен до утверждения схемы и проверки владельцем проекта.
- `supabase/patches/20261115_initiatives_cloud.sql`: подготовлен аддитивный SQL-патч для внутреннего каталога предложений. Он не заменяет и не пересоздаёт текущие таблицы.

## Безопасность патча
- Только авторизованный пользователь может создать запись от собственного `auth.uid()`, со статусом `review`.
- Пользователь видит только опубликованные предложения и собственные; проверяющий видит записи для модерации.
- Изменять статус и заметку модератора может только подтверждённый проверяющий через существующую функцию проверки роли.
- Нет публичной таблицы голосов, подписей, обращений о травле или иных чувствительных сообщений.
- Не сохраняются email и телефон из текста; клиентская проверка — дополнительная мера, основная граница доступа — RLS.
- Это внутренние предложения, не юридические петиции.

## Что ещё не подключено
- Облачная загрузка мероприятий и списков участников: действующая таблица `events` пока не содержит даты, описания, площадки и вместимости, а локальный UI использует демонстрационные записи.
- Облачные проекты и команды: отдельной таблицы в текущей БД нет.
- Новости, опросы, выборы: пока локальные демо-модули.
- Внешний ИИ выключен; Edge Function не развёрнута.
- Каталог школ пуст, поэтому школьная принадлежность не подтверждается автоматически.

## Почему патч пока не применён
Он содержит персональные идентификаторы авторов (Supabase Auth user IDs) и начинает сохранять ученические предложения. Для работы с данными несовершеннолетних нужен назначенный взрослый оператор/владелец проекта, утверждённая политика обработки данных, порядок модерации и проверка требований Кыргызской Республики. Поэтому SQL подготовлен, но live-база не менялась, а feature flag оставлен выключенным.

## План следующего технического этапа
1. После одобрения ответственного взрослого применить патч в тестовой среде на синтетических аккаунтах.
2. Проверить RLS сценариями: гость, автор, другой ученик, проверяющий.
3. Подключить UI списка предложений и модерацию, затем закрыть возможность публикации до модерации.
4. Спроектировать облачную модель проектов/команд.
5. Расширить текущие события аддитивно, не создавая вторую параллельную таблицу мероприятий.
6. Только после отдельного согласования проектировать выборы и чувствительные каналы обращений.

## Проектная лаборатория — технический каркас подготовлен

Добавлен аддитивный патч `supabase/patches/20261115_project_lab.sql`:
- `student_projects`: проектная заявка со статусами review/published/rejected/completed.
- `project_tasks`: задачи проекта.
- `project_join_requests`: приватные заявки учеников на вступление в опубликованный проект.

RLS:
- проект виден после публикации, либо его автору/проверяющему;
- создать проект можно только от собственного `auth.uid()` и только со статусом review;
- задачи читаются только в опубликованных проектах, автором проекта или проверяющим; создавать/менять задачи может автор проекта;
- заявки на вступление доступны подавшему, владельцу проекта и проверяющему;
- пользователь может только отозвать собственную ожидающую заявку; принять/отклонить её может владелец проекта.

Клиентский слой:
- `cloud.js`: `listProjects()`, `createProject()`, `requestToJoinProject()`.
- `app.js`: форма создания проекта и кнопка вступления поддерживают облачный режим при включённом feature flag.
- `supabase-config.js`: `enableCloudProjects: false`, пока патч не применён и не протестирован.

Проверка: SQL-патч выполнен в транзакции `BEGIN … ROLLBACK`; синтаксис и зависимости прошли. Транзакция откатилась, рабочая база осталась без изменений. Не проводились тесты реальных пользовательских сессий и UI браузера.

Ограничения текущего первого этапа:
- Командная функция пока реализована как приватная заявка на вступление, а не автоматическое добавление участника.
- Созданные проекты отправляются на модерацию и не появляются в общем каталоге до публикации.
- Школьные/районные привязки пока не проверяются по утверждённому каталогу.
- Нельзя использовать этот модуль для чувствительных сообщений, официальных выборов или публикации личных контактов.


## Облачный календарь мероприятий — технический каркас подготовлен

Добавлен аддитивный патч `supabase/patches/20261115_events_cloud.sql`:
- расширяет существующую `events` описанием, датой, местом, вместимостью и территорией; вторую таблицу мероприятий не создаёт;
- `create_platform_event(...)` проверяет право организатора через существующую `can_manage_events()`;
- `register_for_event(...)` требует авторизацию, проверяет открытость события, дату, лимит мест и повторную активную регистрацию; блокирует строку события при регистрации, чтобы не превысить вместимость при параллельных запросах;
- регистрация создаётся от `auth.uid()`, публичное согласие на отображение имени принудительно остаётся false.

Клиентский слой:
- `cloud.js`: `listEvents()`, `createEvent()`, `registerForEvent()`, `listMyRegistrations()`.
- `app.js`: существующие формы создания события и регистрации поддерживают облачный режим.
- `supabase-config.js`: `enableCloudEvents: false`; облачный режим выключен.

Существующая схема регистрации уже ограничивает чтение собственными записями или организатором через `can_manage_events()`. Существующая функция `get_event_roster(p_event_key)` возвращает организатору закрытый список с учётом согласия на отображение имени; перед реальным запуском требуется отдельное тестирование этого RPC на разных ролях и на конкретное событие.

Проверка: SQL-патч выполнен в `BEGIN … ROLLBACK`, без фиксации изменений в live-базе. UI и сценарии с реальными аккаунтами не тестировались. Число зарегистрированных участников пока не отображается в публичном календаре; закрытый список и подсчёт требуют проверки прав конкретного организатора, а не только общего административного доступа.

Перед пилотом требуется взрослый владелец проекта, утверждённая политика обработки данных несовершеннолетних, проверка сроков хранения и порядка доступа к спискам. До этого feature flag остаётся выключенным.
