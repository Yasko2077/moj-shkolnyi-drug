## 3. Найденные риски и блокеры

### B1. История SQL не является готовой миграционной последовательностью
В репозитории есть `schema_mvp07.sql`, `schema_mvp09.sql` и множество файлов `supabase/patches/*.sql`. В заголовках схем есть условия о применении после предыдущих базовых схем. Нельзя считать их независимыми миграциями и запускать все подряд. Перед запуском требуется:
1. получить read-only снимок таблиц, колонок, индексов, constraints, policies, функций и grants из целевого проекта;
2. сопоставить его с каждой версией SQL;
3. определить baseline и порядок миграций;
4. проверить upgrade на пустой staging-базе и на копии текущей схемы.

### B2. Авторизация администратора
Клиентский флаг `isAdmin` используется для скрытия/показа действий, но он не является границей безопасности. Каждая операция управления должна быть защищена внутри RPC/политик БД. Проверить отрицательные сценарии: обычный ученик не может назначить школу, публиковать новости, создавать опросы, менять этап выборов или рассматривать заявки.

### B3. Списки участников мероприятий
Клиент получает roster через `get_event_roster`, а регистрация требует отдельного согласия на передачу минимальных данных организатору. Нужно проверить:
- организатор видит только список своего мероприятия;
- посторонний участник не может получить список;
- согласие хранится доказуемо и относится к конкретному мероприятию;
- публичный интерфейс показывает агрегированное число, а не персональные данные.

### B4. Публикация новости — исправлено в коде, ожидает staging
Первоначально `createNews` выполнял insert черновика и отдельный update публикации. В коммите `208c9c9` клиент переведён на единый RPC `publish_news_post`; SQL для атомарной публикации и отзыв прямых клиентских write-прав добавлены в `20261116_news_publish_atomic.sql`. Статические CI-проверки проходят. **Это исправление пока не развёрнуто в Supabase**, поэтому до staging-применения флаг контента остаётся выключенным.

### B5. ИИ и передача данных внешнему обработчику
Edge Function проверяет Bearer-сессию, валидирует длину сообщения, фильтрует очевидные контактные данные, ограничивает историю и вызывает quota RPC. Однако:
- фильтр контактов не является гарантией анонимизации;
- текст запроса и история передаются внешнему поставщику модели;
- необходимо проверить реальные лимиты квоты и устойчивость к параллельным запросам;
- CORS allowlist должен содержать только production/staging домены; локальные origins допустимы только для разработки;
- hosted AI остаётся выключенным до согласования трансграничной обработки данных и политики хранения.

### B6. Выборы — отдельный высокий риск
В SQL присутствует модель этапов выборов, eligibility, кандидатов, бюллетеней и апелляций. Это не подтверждает криптографическую тайну голосования, защиту от связывания личности с бюллетенем, корректность подсчёта и независимость администрирования. Флаг `enableCloudElections` должен оставаться выключенным до отдельного threat model, независимой проверки и письменного одобрения уполномоченной организации.

### B7. Секреты
В браузере допустим только publishable/anon ключ с корректными RLS. Service-role/secret ключи должны храниться только в защищённых серверных secrets. Не отправлять их в чат, Git или клиентские файлы.

## 6. Последовательность production-работ

1. **Schema reconciliation** — фактическая база против репозитория; без изменений данных.
2. **Migration baseline** — собрать воспроизводимую последовательность миграций с проверками preconditions.
3. **Authorization hardening** — RLS, grants, SECURITY DEFINER, индексы, аудит действий.
4. **Staging integration** — отдельный проект, синтетические аккаунты, CI и E2E.
5. **Core release** — Auth, профили, школы, инициативы, проекты, мероприятия, новости.
6. **AI release** — только после privacy review, серверной квоты, origin allowlist и согласования поставщика.
7. **Elections release** — отдельная независимая проверка; не часть первого запуска.

## 8. Проверка после первичного аудита и выполненные исправления

При углублённом чтении SQL-патчей подтверждены два конкретных несоответствия/риска:

1. Исторический патч мероприятий создавал старую перегрузку `register_for_event(uuid,text,text,text,text,text)`, тогда как актуальный клиент использует consent-based `register_for_event(uuid,boolean)`. Поздний патч уже удалял старую перегрузку, но итоговая последовательность должна гарантировать это явно.
2. Публикация новости выполнялась двумя клиентскими запросами. Это создавало промежуточное состояние и требовало прямого UPDATE-доступа к таблице новостей.

В рабочую ветку добавлен файл `supabase/patches/20261116_news_publish_atomic.sql`:
- явно удаляет старую перегрузку регистрации;
- добавляет `publish_news_post(text,text,text)` с серверной проверкой `is_verification_representative()`;
- создаёт и публикует новость одной транзакцией;
- отзывает прямые INSERT/UPDATE/DELETE права клиента на `news_posts`.

Клиентский `cloud.js` переведён на вызов нового RPC. В `scripts/check-project.mjs` добавлены статические регрессионные проверки этих гарантий.

**Важно:** этот патч пока только подготовлен в Git. Он не применён к облачной базе. Его порядок относительно исторических SQL-файлов необходимо подтвердить в migration baseline и на staging. До этого публикация новостей в уже работающем облачном окружении может не соответствовать новому клиентскому коду; feature flag контента должен оставаться выключенным.

### Важное различие исторической схемы

`supabase/schema_mvp07.sql` явно относится к прежней модели: использует `platform_admins` / `is_platform_admin()`, `platform_events` / `platform_event_registrations` и старую модель выборов. Текущий `cloud.js` обращается к `events` / `event_registrations` и проверяет `is_verification_representative()`. README также предупреждает, что `schema_mvp07.sql` и `schema_mvp09.sql` не являются инструкцией для текущей рабочей схемы. Их нельзя применять как baseline текущего backend.

### Отсутствующий артефакт для воспроизводимости

В дереве этой ветки нет актуального исходного SQL-файла базовой схемы, который полностью создаёт используемые базовые таблицы `profiles`, `schools`, `role_assignments`, `events` и `event_registrations`, а также исходные helper-функции. README описывает существующую базу, но описание не заменяет DDL. Поэтому миграционный baseline нельзя безопасно собрать только из доступных в репозитории файлов. Следующий обязательный шаг — получить от взрослого владельца проекта read-only экспорт схемы (DDL без строк данных) из Supabase и сверить его с этими патчами.

## 10. Read-only проверка фактического Supabase (2026-11-15)

Выполнена инвентаризация удалённого проекта через read-only операции: список таблиц/колонок/FK, migration history, функции и их ACL, RLS policies, column grants, Security Advisor, Performance Advisor и список Edge Functions. SQL-изменения не выполнялись; значения пользовательских строк не читались.

### 10.1. Фактическая база

- Migration history API вернул пустой список (`migrations: []`). Это не доказывает, что база пуста; таблицы и функции уже существуют. Историю нужно восстановить/сверить отдельно, а не считать патчи применёнными.
- В `public` обнаружены базовые таблицы: `schools`, `profiles`, `role_catalog`, `role_requests`, `role_assignments`, `events`, `event_registrations`.
- `events` сейчас имеет только базовые поля `id,event_key,title,is_open,created_at`. Расширенные поля календаря из патчей отсутствуют.
- `event_registrations` содержит старую модель с пользовательскими полями и `public_name_consent`; поля `organizer_access_consent` и `organizer_access_consent_at` отсутствуют.
- Таблицы initiatives, projects, news, polls, elections и AI quota в фактическом списке не обнаружены.
- Edge Functions API вернул пустой список; `yntymak-assistant` в проекте пока не развёрнута.
- Схема и metadata подтверждают, что `schema_mvp07.sql` не соответствует действующей модели. В рабочей базе используется `events/event_registrations`, а не старые `platform_events/platform_event_registrations`.

### 10.2. Обнаруженные блокирующие риски текущей event-схемы

**LIVE-EVENT-01 — прямой INSERT в регистрации обходит RPC.** В базе у роли `authenticated` есть column-level INSERT на `event_registrations`, а RLS policy `event_registrations_insert_self` разрешает вставку строки с `user_id=auth.uid()` и `status='registered'`. Это позволяет обойти серверную проверку лимита мест, проверку профиля и отдельное согласие на доступ организатора. Нужен отзыв прямых INSERT/UPDATE/DELETE и регистрация только через проверенный RPC. Подготовленный патч `20261115_event_registration_hardening.sql` делает отзыв прямых write-прав, но пока не применён.

**LIVE-EVENT-02 — устаревший roster RPC имеет слишком широкую область доступа.** Фактическая функция `get_event_roster(p_event_key text)` возвращает персональные поля всем пользователям, для которых `can_manage_events()` истинна. Эта функция считает полномочными роли `event_organizer`, `school_president`, `city_council_chair`, `city_council_deputy`, `district_chair`, `city_chair` без проверки соответствия конкретному мероприятию, школе или району. Нужна замена на UUID-scoped `get_event_roster(uuid)` с проверкой создателя события и действующей территориальной роли. Подготовленный `20261115_event_roster_scope.sql` реализует более узкую проверку, но пока не применён.

Оба риска относятся к текущей схеме Supabase независимо от того, что клиентские cloud feature flags выключены. До исправления нельзя включать облачную регистрацию мероприятий или показывать roster реальным пользователям.

### 10.3. Security Advisor

Зафиксированы:
- 5 предупреждений `authenticated_security_definer_function_executable`: `can_manage_events()`, `create_my_profile(...)`, старый `get_event_roster(text)`, `is_verification_representative()`, `review_role_request(...)`. Наличие EXECUTE для authenticated само по себе не доказывает уязвимость; функции требуют индивидуальной проверки контракта, ACL и проверок `auth.uid()`. Для старого roster подтверждён риск из LIVE-EVENT-02.

## 11. Дополнительное усиление миграций: column-level grants

В ходе проверки выяснилось, что исторические патчи выдавали права на отдельные столбцы (например, INSERT для полей `news_posts` и `poll_options`). Обычный `REVOKE INSERT/UPDATE ON TABLE` не следует считать достаточным доказательством отзыва таких отдельных разрешений.

В рабочую ветку внесены дополнительные явные отзывы column-level прав:
- `20261115_event_registration_hardening.sql`: отзывает INSERT/UPDATE по всем клиентским полям регистрации и блокирует старый `get_event_roster(text)` до установки UUID-scoped функции;
- `20261116_news_publish_atomic.sql`: отзывает column-level INSERT/UPDATE новостей после перехода на атомарный RPC;
- `20261115_poll_option_write_lock.sql`: отзывает column-level INSERT/UPDATE вариантов опросов;
- `20261115_profile_school_integrity.sql`: сначала сбрасывает прежние UPDATE-разрешения по всем полям профиля, затем выдаёт allow-list только для имени, языка и класса.

В `scripts/check-project.mjs` добавлены статические проверки наличия этих отзывов. В `docs/SECURITY_TEST_MATRIX.md` добавлены отрицательные проверки через `has_column_privilege`.

**Ограничение:** эти изменения пока находятся только в Git. Они не были применены ни к рабочей базе, ни к staging. Синтаксис SQL и фактический результат grants должны быть проверены на staging после получения воспроизводимого базового DDL.

## 13. Сверка модели мероприятий с фактическим ограничением базы

Фактическая таблица `events` содержит уникальное ограничение `events_event_key_key`. При этом `event_key` — категория (`forum`, `media`, `debate`, `eco`), а актуальный интерфейс и scoped roster рассчитаны на несколько отдельных мероприятий одной категории с адресацией по UUID. Старое уникальное ограничение конфликтовало с этой моделью и не позволяло создать второе мероприятие той же категории.

В `20261115_events_cloud.sql` добавлено удаление `events_event_key_key` перед расширением таблицы. Это не удаляет события или их данные, но меняет правило уникальности категории. На staging нужно проверить создание двух разных мероприятий с одинаковым `event_key`, после чего получить списки по разным UUID. Изменение не применено к рабочей базе.
