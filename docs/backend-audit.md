# Ынтымак — технический аудит backend (предварительный)

Дата проверки: 2026-11-15  
Ветка: `test/yntymak-supabase-audit`  
Область: исходники `cloud.js`, SQL-схемы/патчи в `supabase/`, Edge Function `yntymak-assistant`.

> Это статический аудит репозитория, а не подтверждение состояния удалённой базы. SQL в Supabase не запускался, реальные пользовательские данные не читались, миграции не применялись.

## 1. Краткий вывод

В проекте уже есть заметный backend-фундамент: Supabase Auth, профили, каталог школ, предложения, проекты и заявки в команды, события и регистрации, новости, опросы, задел модуля выборов, Edge Function для ИИ. Однако наличие клиентских методов и SQL-файлов ещё не означает, что функции согласованы с фактической облачной схемой или безопасно готовы к запуску.

**Production gate: закрыт.** До реального запуска необходимы:
- инвентаризация фактической схемы Supabase и сопоставление с SQL из репозитория;
- единый упорядоченный migration baseline (сейчас в проекте есть несколько исторических schema/patch файлов);
- проверка RLS и SECURITY DEFINER функций на реальных ролях в отдельном staging-проекте;
- E2E-тесты с синтетическими аккаунтами;
- решение ответственного взрослого оператора по размещению и обработке данных несовершеннолетних.

## 3. Найденные риски и блокеры

### B1. История SQL не является готовой миграционной последовательностью
В репозитории есть `schema_mvp07.sql`, `schema_mvp09.sql` и множество файлов `supabase/patches/*.sql`. В заголовках схем есть условия о применении после предыдущих базовых схем. Нельзя считать их независимыми миграциями и запускать все подряд. Перед запуском требуется:
1. получить read-only снимок таблиц, колонок, индексов, constraints, policies, функций и grants из целевого проекта;
2. сопоставить его с каждой версией SQL;
3. определить baseline и порядок миграций;
4. проверить upgrade на пустой staging-базе и на копии текущей схемы.

### B2. Авторизация администратора
Клиентский флаг `isAdmin` используется для скрытия/показа действий, но он не является границей безопасности. Каждая операция управления должна быть защищена внутри RPC/политик БД. Проверить отрицательные сценарии: обычный ученик не может назначить школу, публиковать новости, создавать опросы, менять этап выборов или рассматривать заявки.

### B3. Списки участников мероприятий
Клиент получает roster через `get_event_roster`, а регистрация требует отдельного согласия на передачу минимальных данных организатору. Нужно проверить:
- организатор видит только список своего мероприятия;
- посторонний участник не может получить список;
- согласие хранится доказуемо и относится к конкретному мероприятию;
- публичный интерфейс показывает агрегированное число, а не персональные данные.

### B4. Публикация новости не атомарна
`createNews` сначала создаёт черновик, затем отдельным запросом публикует его. Если второй запрос не пройдёт, останется черновик; если политики позволяют некорректный update, граница полномочий ослабляется. Рекомендуется единый RPC `publish_news_post` с серверной проверкой роли и валидацией.

### B5. ИИ и передача данных внешнему обработчику
Edge Function проверяет Bearer-сессию, валидирует длину сообщения, фильтрует очевидные контактные данные, ограничивает историю и вызывает quota RPC. Однако:
- фильтр контактов не является гарантией анонимизации;
- текст запроса и история передаются внешнему поставщику модели;
- необходимо проверить реальные лимиты квоты и устойчивость к параллельным запросам;
- CORS allowlist должен содержать только production/staging домены; локальные origins допустимы только для разработки;
- hosted AI остаётся выключенным до согласования трансграничной обработки данных и политики хранения.

### B6. Выборы — отдельный высокий риск
В SQL присутствует модель этапов выборов, eligibility, кандидатов, бюллетеней и апелляций. Это не подтверждает криптографическую тайну голосования, защиту от связывания личности с бюллетенем, корректность подсчёта и независимость администрирования. Флаг `enableCloudElections` должен оставаться выключенным до отдельного threat model, независимой проверки и письменного одобрения уполномоченной организации.

### B7. Секреты
В браузере допустим только publishable/anon ключ с корректными RLS. Service-role/secret ключи должны храниться только в защищённых серверных secrets. Не отправлять их в чат, Git или клиентские файлы.

## 4. План проверки в staging

Использовать только синтетические данные и отдельный проект/окружение.

| Проверка | Успешный критерий |
|---|---|
| Регистрация и подтверждение email | Сессия появляется только после предусмотренного auth flow |
| Bootstrap профиля | Повторный вход не создаёт дубликаты; ученик не может назначить себе школу |
| Школьная принадлежность | Только уполномоченный reviewer может назначить школу; действие журналируется |
| Предложение | Автор создаёт; другой ученик видит только разрешённые поля; статус меняет только reviewer |
| Проект и заявка | Дубликат заявки запрещён; только владелец проекта рассматривает заявку |
| Мероприятие | Регистрация идемпотентна; лимит вместимости не превышается при параллельных запросах |
| Список участников | Доступ только разрешённому организатору; нет доступа к другим событиям |
| Новости и опросы | Публикация и создание ограничены ролью; ученик не меняет варианты/результаты |
| AI quota | Лимит атомарен при одновременных запросах; чужая сессия отклоняется |
| RLS | Для каждой таблицы есть positive и negative тесты на anon, ученике, организаторе и reviewer |
| Edge Function | Неизвестный Origin отклоняется; OPTIONS/POST корректны; payload ограничен |
| Backup/restore | Восстановление проверено на staging до запуска |

## 5. Что нужно собрать перед миграцией

Read-only инвентаризация целевой базы:
- `information_schema.tables` и `information_schema.columns`;
- `pg_indexes`;
- `pg_constraint`;
- `pg_policies`;
- `pg_proc` для функций в `public`;
- grants на таблицы, sequence и функции;
- Supabase Security Advisor findings;
- миграционная история и текущий ref проекта.

Не включать real student data в тесты и не экспортировать персональные строки в GitHub issues.

## 6. Последовательность production-работ

1. **Schema reconciliation** — фактическая база против репозитория; без изменений данных.
2. **Migration baseline** — собрать воспроизводимую последовательность миграций с проверками preconditions.
3. **Authorization hardening** — RLS, grants, SECURITY DEFINER, индексы, аудит действий.
4. **Staging integration** — отдельный проект, синтетические аккаунты, CI и E2E.
5. **Core release** — Auth, профили, школы, инициативы, проекты, мероприятия, новости.
6. **AI release** — только после privacy review, серверной квоты, origin allowlist и согласования поставщика.
7. **Elections release** — отдельная независимая проверка; не часть первого запуска.

## 7. Ограничения текущего аудита

- Не выполнялись SQL-запросы к удалённой базе и не применялись патчи.
- Не подтверждена совместимость всех RPC с фактической базой.
- Не выполнен браузерный E2E-тест в Safari.
- Статический анализ не заменяет тестирование RLS от имени разных ролей.
- Не проводилась юридическая оценка законодательства Кыргызстана; этот документ — технический, а не юридическое заключение.


## 8. Проверка после первичного аудита и выполненные исправления

При углублённом чтении SQL-патчей подтверждены два конкретных несоответствия/риска:

1. Исторический патч мероприятий создавал старую перегрузку `register_for_event(uuid,text,text,text,text,text)`, тогда как актуальный клиент использует consent-based `register_for_event(uuid,boolean)`. Поздний патч уже удалял старую перегрузку, но итоговая последовательность должна гарантировать это явно.
2. Публикация новости выполнялась двумя клиентскими запросами. Это создавало промежуточное состояние и требовало прямого UPDATE-доступа к таблице новостей.

В рабочую ветку добавлен файл `supabase/patches/20261116_news_publish_atomic.sql`:
- явно удаляет старую перегрузку регистрации;
- добавляет `publish_news_post(text,text,text)` с серверной проверкой `is_verification_representative()`;
- создаёт и публикует новость одной транзакцией;
- отзывает прямые INSERT/UPDATE/DELETE права клиента на `news_posts`.

Клиентский `cloud.js` переведён на вызов нового RPC. В `scripts/check-project.mjs` добавлены статические регрессионные проверки этих гарантий.

**Важно:** этот патч пока только подготовлен в Git. Он не применён к облачной базе. Его порядок относительно исторических SQL-файлов необходимо подтвердить в migration baseline и на staging. До этого публикация новостей в уже работающем облачном окружении может не соответствовать новому клиентскому коду; feature flag контента должен оставаться выключенным.
